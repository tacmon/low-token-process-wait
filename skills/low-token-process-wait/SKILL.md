# 长程序等待与原任务定时继续

本配置偏好自动安排官方定时跟进。Goal 暂停/恢复需要用户授权；已有明确授权时不重复询问。用于有限的非交互任务；不用于常驻服务器、需要输入的程序或等待审批的操作。

## 能力边界

- Desktop Linux：已实测普通对话结束后，后台程序继续运行，官方 heartbeat 返回同一任务，验证输出并停用定时任务。使用宿主调度，不需要 CLI/tmux 或新会话。
- Desktop Goal：定时回调与 Goal 恢复是两回事。已有回调进入 paused Goal 的证据，但没有恢复 active 的验证；当前仅有暂停工具时，不能承诺自动暂停/恢复闭环。
- CLI：支持的本地交互环境中，进程退出监督器与同一 Goal 暂停/恢复已有实测；它是退出事件唤醒，不是 Desktop 的定时轮询。

后台程序、调度创建、自动回调和后续处理必须分别验收。详细证据和演示步骤见 [Desktop 验证与演示](references/desktop-validation.md)。

## 下一次等待：预测优先，未知时退避

**每次取得当前状态后，先判断能否可信地估计程序还需多久结束，再决定下一次等待。** 不强制所有程序先等30秒，也不要求先走完退避档位。用户另行指定的节奏优先。

| 当前判断 | 下一次等待 |
| --- | --- |
| 已结束或失败 | 立即核验退出记录和输出，继续原任务或处理失败 |
| 可信剩余时间 R > 0 | 直接等待 R，在预计完成时刻检查，不设30分钟上限 |
| 无法可信估计 | 按未知时退避序列选择下一档 |

**已知 ETA 不局限于退避取值。** 例如预计还需7分钟就等7分钟，预计还需18分钟就等18分钟；预计还需50分钟就等50分钟，预计还需3小时就等3小时。默认不提前唤醒，也不在中间每30分钟重新评估。这里的 R 是从当前时刻到完成的剩余时间，不是程序总耗时，也不是上一轮记录的原始 ETA。

默认接受预测等待的代价：提前完成或中途失败可能直到预计完成时刻才被发现。已有可靠的退出事件唤醒继续保留，提前退出即可处理，不为遵守 ETA 延迟处理。预计时刻检查后，已结束则核验并继续；未结束则用新证据重估并安排下一次等待。只有无法可信预测时才采用下述退避及最终30分钟循环。宿主无法支持所需跨度时明确报告实际限制，不将其描述为本技能的30分钟上限。

### 怎样估计剩余时间

优先采用程序给出的可信 ETA、确定的结束时刻，或同一阶段的带时间戳进度和近期吞吐量。已知总工作量时，可用剩余工作量除以近期处理速度；估计要包括尚未开始的阶段和排队工作，并考虑真实并行度，不能把一个 worker 的进度当成整个程序的完成比例。

- 同类历史耗时可以辅助，但必须核对输入规模、阶段和资源是否可比；单个进度点、仅凭“仍在运行”、文件更新时间或猜测不够支持 ETA。
- 若单步代价在增加、阶段切换或吞吐不稳定，不能盲目按全程平均速度线性外推。没有可靠的阶段模型或可比样本就标为未知，不编造精确预测。
- 记录估计依据、采样时间和预计完成时刻。每次探测都用新证据重算；过期 ETA 不能直接减成0秒然后密集检查。预计时刻已过但仍运行时，更新预测；无法解释偏差时回到未知退避。

### 无法预测时的退避序列

相邻探测的等待间隔依次为 **30秒 → 1分钟 → 2分钟 → 5分钟 → 10分钟 → 30分钟 → 30分钟……**。不是从启动时刻起的绝对偏移；忽略开销时累计探测点为30、90、210、510、1110、2910秒……。

| 未知档位 | 本档等待 |
| --- | --- |
| 0 | 30秒 |
| 1 | 1分钟 |
| 2 | 2分钟 |
| 3 | 5分钟 |
| 4 | 10分钟 |
| 5 | 30分钟，之后保持 |

只有按未知策略安排的那次等待到期、探测仍未完成且依旧无法估计时，才推进一档。获得可信 ETA 就立即转为预测优先，不继续机械退避。预测再次失效时从保存的下一未知档位继续；从未使用过未知退避则从档位0开始。日志增长、普通状态询问和重复回调均不重置或重复推进档位。

### 执行与状态保存

- 下一次等待不超过30秒时，优先在当前会话等待已有执行会话的退出事件，不创建自动任务；没有退出事件等待时，用可被用户输入打断的等待工具，到期检查一次。程序提前退出立即处理，不等满间隔。初次未知策略的30秒预算计入启动调用已等待的时间；可信 ETA 则按当前采样时刻计算，不能重复扣除同一段时间。
- 更长等待在宿主允许时用同任务官方调度。若工具只支持整分钟，将 R 向上取整到最近支持的分钟，可信 ETA 不按30分钟截断；例如2分10秒设为3分钟，而不是5分钟。记录目标间隔与实际生效间隔，不宣称精确秒级回调。工具无法表示要求时报告限制，不偷偷保留旧频率。
- 正在处理独立工作时无需空等；到期检查一次并记录实际时间。迟到回调只检查一次，不补发错过的探测。新接管已有作业先读取状态和等待记录，不重启程序；优先重新估计，而非一律从30秒开始。
- 在项目允许写入的位置保存简短等待记录：稳定作业标识、PID及创建时间/命名空间、主机、执行会话、日志/退出码/结果路径；当前策略（ETA或未知）、ETA及依据/采样时间/预计完成时刻、下一未知档位、最近探测时间、目标与实际间隔、下次探测时间、automation id、完成后的下一步。
- 每次有效探测都执行“检查状态 → 重新判断 ETA → 计算下一等待 → 同步实际调度 → 保存确认结果”。**只改技能文件、提示词或本地状态不等于已经改了调度。** 重新应用本技能于既有等待任务时，核对其实际配置并在宿主允许范围内更新同一个任务，不能让历史5分钟频率永远延续。
- 完成或失败立即停止等待并核验结果；需要交互或审批时退出非交互等待流程。纯等待无新情况时保持安静。

**先检查宿主边界。** 只有当前系统/开发者指令允许为此类有限程序创建或更新跟进自动任务，且官方工具支持所需节奏时，才使用下面的 Desktop 调度流程。用户偏好、过去的实测和工具可见均不覆盖当前宿主限制；若当前宿主禁止单个作业完成监控自动化，不能创建、恢复或改名绕过限制。在当前任务中继续受支持的等待：保持上述业务探测间隔，单次阻塞等待不超过60秒，长间隔分段等待，中间不额外读取业务状态；按当前沟通要求提供必要更新，不能声称已安排后台续跑。支持的 CLI 可用下述退出事件路径。

## Desktop 官方调度路径（仅在宿主允许时）

按上述决策得到超过30秒的等待时间时，主动安排官方调度；已有可信 ETA 时可以直接安排，不必先做30秒探测。不依赖用户每次说“设个定时任务”。CLI 路径仍仅通过交互式输入框。禁止用非交互 Codex 命令、SDK 或自建模型客户端替代。

1. 确认工作程序能够在本轮结束后继续运行，记录真实 PID（含创建时间或稳定任务标识）、主机、项目、日志、结果/退出状态文件和完成后的下一步；已经运行的任务不得重跑，工具会话句柄不是 PID。沙箱内 PID 还可能属于独立命名空间，不能用它操作宿主进程。优先使用宿主保留的执行会话或已验证的作业服务；仅调用 Popen/start_new_session/nohup 不足以证明任务能跨工具调用存活。记录启动标记，必要时做一次有限检查；已启动的任务不得重复运行。
2. 查找当前暴露的 automation_update 工具，按实际 schema 使用 kind=heartbeat、绑定当前任务。优先更新同一工作已有的自动任务；若需要查找已有记录，在 CODEX_HOME/automations/*/automation.toml 中匹配任务标识，不重复创建。不要写原始调度配置文件，不以独立 cron/新任务替代原任务心跳。
3. 按“预测优先，未知时退避”设置下一次等待。每次都核对实际生效间隔与当前决策，保留同一个任务标识、绑定会话及通知偏好。不要为各个档位创建多个任务，也不能只更新提示词而不更新周期。若间隔无需变化，不做重复更新。宿主要求审批时遵循实际审批流程，不假称已创建或更新。
4. 自动任务提示词包含真实监视对象、等待记录路径、ETA优先规则、未知退避序列、退出记录读取方法及后续动作。每次只检查一次；未结束则重新估计、选择间隔并同步调度，保存工具确认结果后结束本轮，不在回调里同时启动另一套轮询。下一等待≤30秒时，按短等待路径执行并停用重复的后台检查；只能保留一个等待机制。重复/提前回调根据记录去重。没有可行动变化时不发送进度汇报；完成、失败或需用户行动时才通知。进程消失不能当作成功，须核验退出记录和输出；无法取得退出码时说明 unknown。完成后继续原任务，并暂停或删除这次等待专用自动任务，记录真实 automation id。
5. 工具返回创建/更新成功后结束当前回答；初次说明下次检查间隔及依据（预计剩余时间或未知退避），后续无变化回调保持安静。不要同时开启 CLI 监督器、子 agent 监视或前台轮询。创建/更新失败时报告原因并保存实际仍生效的配置，不把计划间隔当成已更新；必要时停用遗留高频任务，不能声称定时唤醒已生效。
6. Goal 与定时任务是独立生命周期。不能假定结束回答会让 active Goal 停止自动续跑，也不能假定定时消息会把 paused Goal 改为 active。只有当前宿主具备可验证的原 Goal 暂停与恢复路径时才进行自动联动；即使用户允许临时暂停，也不能凭授权创造缺失的恢复工具。若不具备该路径，明确说明 Goal 联动尚未验证，不能承诺停等和自动恢复，不能把 Goal 标记 complete/blocked 来模拟等待。

### 显式诊断实验

用户明确要求验证 Goal 与定时任务联动时，允许先做仅包含“记录身份 → 创建当前任务 heartbeat → 暂停 Goal → 自动唤醒读取状态 → 保存诊断记录 → 停止 heartbeat”的隔离实验。不能因为没有恢复工具而拒绝这个不执行恢复的诊断；不要启动长任务，也不要声称其证明恢复能力。回调可执行用户单独授权的诊断动作，不自动推进已暂停的原 Goal。需要明确区分：原会话收到定时输入、回调执行、原 Goal 恢复 active，三者是独立验收项。日常自动暂停/恢复仍须有可验证恢复路径；诊断成功不取消该要求。

2026-10-07：Desktop Linux 26.917.71314（build 10954）已完成90秒后台程序、2分钟 heartbeat、原对话回调、结果核验及自动停用的闭环实测；该测试没有 Goal。

v0.6.1 的无30分钟上限 ETA 等待及含10分钟档的未知退避尚未完成真实调度时序验收，不能用上述固定2分钟实验替代其证据。[官方文档](https://learn.chatgpt.com/docs/automations?surface=app)说明会话内调度支持分钟级间隔；这不保证当前宿主允许该用途，也不证明修改间隔后精确从修改时刻计时。

官方调度会定期运行模型，不保证零 token 或进程退出立即唤醒。本地任务要求电脑和 Desktop app 持续运行。当前 Desktop 已在真实任务中创建定时跟进，并在2026-09-29的隔离诊断中实际收到官方 heartbeat：回调在原任务执行，Goal 在回调读取时仍为 paused，目标文本及创建时间一致。该结果证明暂停 Goal 不阻止此次定时回调，但该次诊断不证明恢复 active 或全区间没有其他轮次；缺失的独立调度审计仍为未验证。该诊断结束后其定时任务已删除，不自动重新创建。

## CLI 自动路径

在尚未交给退出监督器、且当前会话可观察已启动程序时，先按预测优先规则判断：可信 ETA≤30秒或首次未知可短等；更长等待直接接管已有程序，不必为了退避表先等30秒，不重跑。已由支持的 CLI 退出监督器包装的任务保留退出即唤醒，不叠加分钟级定时探测，也不为走完退避表延迟处理完成事件。退避表用于需要定时探测的路径，不替代已有退出事件机制。

监督脚本现在优先以只读方式从 goals_1.sqlite 取得真实 goal_id 和创建时间；工具创建的 Goal 不一定在会话日志中产生 thread_goal_updated。数据库存在但身份读取失败时仍拒绝操作，不用旧日志覆盖当前身份。暂停/恢复仍仅通过原 CLI 输入框，不修改数据库。该修复已通过180秒真实CLI重测：完成消息一次、同一Goal恢复并续跑完成；不据此承诺精确恢复时序或任何环境下零模型活动。

1. 使用退出监督器启动时，启动前包装；已有程序需要较长等待或短等待后仍未结束时，取得真实操作系统 PID 并接管，不能重跑原命令。工具 session_id 不是 PID。远程 PID 不能在本机监视。
2. 确认当前是本机 Linux 交互式 CLI，环境有 TMUX、TMUX_PANE、CODEX_THREAD_ID；缺失时报告限制，不猜目标，不操作别的会话。可按 references/operation.md 安装可选 zsh 启动入口；不能假定安装 skill 就已经修改用户 shell。
3. 使用以下已安装脚本，定位参数默认读取上述环境，结果放在当前项目允许写入的目录：

   ```bash
   /usr/bin/python3 "${CODEX_HOME:-$HOME/.codex}/skills/low-token-process-wait/scripts/wake.py" start --state-dir "$PWD/.codex-wake-jobs" -- 原命令 参数
   ```

   当前有 active Goal 且已获临时暂停/恢复授权时，在 -- 前加 --goal。已运行任务用 --attach-pid 实际PID --attach-log 实际日志绝对路径 替代 -- 原命令 参数；没有日志则省略 --attach-log。不得传入示例 PID。
4. 返回监督 PID 和结果路径后立即结束本轮，告知已交给本地监督程序以及结果位置。不要等待、反复查状态、启用子 agent 监视或创建定时模型检查。不要标记 Goal complete/blocked 来模拟等待。监督程序会通过同一 CLI 输入框暂停 Goal，等回答结束后运行任务。
5. 收到 Job wake-... finished 消息后，读取对应结果和日志，继续原工作。这只是进程结束通知；接管非子进程退出码为 unknown，不能编造成功。使用 --goal 时，恢复由监督程序负责，不手动清除、替换或恢复 Goal，不改变目标创建时间。不要依赖“本次完成消息回答结束后才恢复”的精确时序：实测首次读取时可能已经 active。若仍 paused，处理结果后结束回答，让监督程序恢复；若已 active 且监督结果已 delivered、goal_restored=true，可继续原目标。未验收原目标全部要求前不得完成 Goal。

上述 CLI 方案的所有模型交互只走原交互式 CLI 输入框和 Enter。不得用 codex exec、queue、SDK、app-server 客户端、模型 HTTP 调用或其他模型替代。等待期间由本地脚本等进程退出，不运行模型。

## 失败与边界

- 沙箱隐藏宿主 PID 或禁止访问 tmux 时注册失败。不得自动提升权限、绕过沙箱或重新运行已经启动的任务；报告具体原因。用户原来明确选用 full-access 时按该权限执行，skill 不改变权限设置。
- attention 保留结果且不自动重复投递。先核实原会话是否已经收到消息，再处理恢复；不能盲目重跑。
- 默认英文 CLI 布局已实测。窄窗口、草稿、复制模式、其他布局、会话或 Goal 被用户改变时可能拒绝投递。主机必须运行、CLI 面板必须保留。进程消失不等于成功。
- Desktop 输入框自动控制未实现；按预测优先规则选择等待，仅在宿主允许时采用上述官方调度，而非 CLI tmux 监督器。当前宿主禁止该用途或缺少工具时明确报告，不假装已安排。
- 无法后台唤醒但仍可在当前任务等待时，按上述分段等待路径继续，不改成高频探测。连当前任务等待也不受支持时，非 Goal 可给出已有 scripts/wait_pid.py 的真实 PID 命令，请用户结束后通知；有 active Goal 时说明限制，征求是否暂停等待人工通知。

## WezTerm 日常使用

按操作说明接入可选 zsh 启动函数后，新终端照常运行 codex 会由 launch_cli.py 建立专用 tmux。此方案依赖 tmux，通过 codex.tmux.conf 保留十万行历史、隐藏底栏、鼠标阅读和剪贴板支持，并默认 --no-alt-screen 内联显示。具体复制键位、退出阅读以及安装/卸载见操作说明。仅改Codex专用服务器，不改WezTerm字体、输入法或标签页设置。历史阅读模式会暂缓自动投递，退出阅读后再继续。不能保证完全等同于原生终端；内联模式尚未重复完整Goal实测。其他用户安装skill不会自动安装shell函数，不可假称已接入。

启动环境、权限和卸载方法参见 [references/operation.md](references/operation.md)，需要时读取。
